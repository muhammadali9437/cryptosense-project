\section{Introduction}
\subsection{Background}
Cryptocurrency markets operate continuously and expose users to fast price changes, high volatility, information overload and uneven data quality. The project consolidates live market observations and contextual indicators into a dashboard. It presents signals with explanations and risk factors, explains forced liquidations in the futures market, and offers educational and simulation features that help users understand market mechanics without placing real trades.

\subsection{Problem Statement}
An individual observer may switch among exchanges, charts, news feeds, liquidation trackers and portfolio records to understand a market move. Raw indicators can be difficult to interpret, uncontextualized AI predictions can mislead, and AI chatbots can produce fluent answers containing invented numbers. CryptoSense addresses this problem by combining a data dashboard, explanatory analytics, portfolio and alert tracking and a paper wallet, while explicitly presenting forecast uncertainty and never displaying made-up data.

\subsection{Aim and Objectives}
\begin{itemize}
\item Build a web interface for live market prices and candlestick data.
\item Integrate REST services with market, news, Fear \& Greed and optional external providers.
\item Engineer indicators and generate a three-class 24-hour market-state signal, or report it as unavailable when a real input is missing.
\item Expose explainable per-coin and portfolio risk scores and a Risk Copilot with history, historical analogs, key levels and what-if analysis.
\item Track, analyse and explain observed futures liquidations with robust statistics and alerts.
\item Support accounts, holdings, price alerts, P\&L limits and optional Telegram notifications.
\item Provide fee-aware simulated trades without exchange execution.
\item Deliver retrieval-grounded chat answers from six specialist analysts, with AI-written numbers checked against computed facts and a rules fallback.
\item Document limitations, operations and interfaces, and the changes since the previous edition.
\end{itemize}

\section{Architecture and Design}
\subsection{Architectural Style}
The system follows a client-server and layered architecture. Flutter manages presentation and local state and reads live prices directly from Binance. FastAPI exposes JSON routers, Pydantic validates contracts, services perform domain operations, SQLAlchemy persists records, and provider adapters retrieve external data. The Predictor loads model artifacts for inference, while a separate command-line pipeline handles model training and evaluation. Five background tasks run inside the backend process.
\diagram{diagrams/01_system_architecture.png}{Major application layers, dependencies and data stores.}{fig:arch}{\linewidth}

\subsection{Backend Request Lifecycle}
The backend request lifecycle consists of the following stages:
\begin{itemize}
\item Startup creates ORM tables, starts the alert (every 30 s), news (every 15 min), listings (every 6 h), liquidation-stream and liquidation-store tasks, and logs model readiness.
\item A request enters a router; FastAPI dependencies supply a database session and, if required, an authenticated user.
\item Schemas validate input; handlers call services and return JSON responses.
\item Services fetch, cache and transform provider data, call Predictor/risk calculations and persist ORM changes.
\item If a signal cannot be computed from real inputs, a \texttt{SignalUnavailable} handler returns HTTP 503 with the missing inputs.
\item Shutdown cancels the background tasks and closes shared Binance clients.
\end{itemize}

\subsection{Relationship and Lifecycle Rules}
The main entity relationships and lifecycle rules are as follows:
\begin{itemize}
\item User 1--many holdings, alerts and notifications; declared ORM cascades apply.
\item User 1--0/1 paper account; one account has many positions and trades.
\item PaperPosition has a unique account\_id + symbol constraint.
\item LiquidationEvent rows are de-duplicated by event\_key and kept for 7 days by default (\texttt{LIQUIDATION\_RETENTION\_DAYS}).
\item Listing uses the exchange symbol as primary key; risk history uses generated row IDs.
\item User and trade data are durable; most market results are fetched, cached or stored as model/JSON artifacts.
\end{itemize}

\subsection{Frontend Class and State Pattern}
The frontend follows a shared state and service pattern:
\begin{itemize}
\item \textbf{CryptoSenseApp} owns MarketService and AppState lifecycles and opens the Shell.
\item \textbf{AppScope} exposes shared services through BuildContext extensions.
\item \textbf{ApiService} maps JSON to Dart types, stores the JWT in SharedPreferences and raises ApiException for HTTP errors.
\item \textbf{MarketService} reads a real Binance snapshot and the live ticker stream; when Binance is unreachable it reports ``unavailable'' and retries instead of simulating prices.
\item \textbf{AppState} (ChangeNotifier) manages authentication, holdings, alerts, refreshes, notification polling and guest state.
\item \textbf{Screens} compose page-level UI; widgets provide reusable charts, cards, badges and controls.
\end{itemize}

\subsection{Authentication and Authorization}
Registration normalizes email, checks uniqueness, hashes with bcrypt and returns an HS256 JWT. Schema validation checks password length and bcrypt's 72-byte limit. Tokens expire after seven days by default. \texttt{current\_user} protects endpoints; \texttt{optional\_user} supports optional authentication (for example chat). User-scoped queries are used for portfolio, alerts and paper trading. A strong, stable \texttt{JWT\_SECRET} must be configured in \texttt{.env}; the built-in default is a public placeholder.

\section{AI, Feature Engineering and Risk}
\subsection{Dataset and Target}
The deployed models were trained on hourly Binance data for BTC, ETH, BNB, SOL, XRP and ADA over 730 days, with funding and Fear \& Greed context. The training script now defaults to ten years of requested history and keeps only hours for which real funding and Fear \& Greed values exist (no filled-in values). The target is the return after 24 hours: greater than $+2.5\%$ is bullish, less than $-2.5\%$ is bearish, otherwise neutral. This is a classification task, not exact-price regression.

\subsection{Training and Inference}
The training and inference process follows these steps:
\begin{itemize}
\item Training downloads candles, funding data and Fear \& Greed data from the real providers; there is no synthetic or demo option.
\item Training and serving share the same feature code. Backward as-of joins avoid using future-known context.
\item A chronological per-coin split is used: 70\% training, 15\% validation and 15\% testing, with a horizon gap. The recorded rows are 72{,}984, 15{,}414 and 15{,}708.
\item XGBoost and LightGBM use validation and early stopping, with class balancing. Ensemble weights come from validation macro-F1.
\item At inference the weighted probabilities give the trend; a bullish or bearish call below 0.55 confidence is shown as neutral.
\item Models and metrics are saved under \texttt{backend/ml/models}; \texttt{POST /api/signals/reload} loads retrained models without a restart.
\end{itemize}

When the models are confident their accuracy rises to 73--78\%, which is why weak directional calls are shown as neutral. These results do not establish reliable profitable direction forecasting. Model confidence is not a guarantee.

\subsection{Risk Copilot}
\texttt{GET /api/risk/\{symbol\}/copilot} combines the risk score with the model votes, the stored risk history, historical market analogs (past hours with similar returns, RSI, ATR, trend, band width and volume, and what happened in the following 24 hours) and UTC key levels (previous day, Asia and London sessions, prior week). \texttt{POST /api/risk/\{symbol\}/simulate} recomputes the score with volatility multiplied by 1.0, 1.5 or 2.0.

\subsection{Sage, Specialists and Grounded Explanations}
For each question six specialists produce deterministic reports from live data: market intelligence, derivatives, on-chain (whales), sentiment and news, risk assessment, and explanation. The KnowledgeBase indexes the Academy, app guide and methodology Markdown documents, recent news and signals with TF-IDF. Sage adds the retrieved material and the specialist reports, then asks Claude (default model \texttt{claude-opus-5-5}); if Claude is not configured or fails, an OpenAI-compatible model (Groq by default); otherwise rules answer. Every number in an AI-written explanation must match a computed fact at the precision written (rounding and K/M/B suffixes allowed); otherwise the AI text is discarded and the rules answer is shown.

\subsection{News Sentiment}
News comes from RSS feeds and, with a key, CryptoPanic. Sentiment uses VADER with a cryptocurrency lexicon. With a TypeSafe key, \texttt{/api/news/compare} compares Jev verdicts with VADER on current headlines. If no news source responds, the API reports news as unavailable.

\section{Liquidation Intelligence}
\subsection{Data Source}
The backend listens to the Binance USD-M futures stream \texttt{!forceOrder@arr}. A forced SELL closes a long position (long liquidation) and a forced BUY closes a short. The USD value is filled quantity times average price, and is marked valid only for stablecoin-margined contracts. Binance sends at most one liquidation per symbol per second, so all figures are \textit{observed stream events}, not exchange-wide totals. The stream reconnects after 300 seconds of silence and gaps are recorded.

\subsection{Statistics and Spike Detection}
Statistics are available for 5-minute, 15-minute, 1-hour, 4-hour and 24-hour windows and for BTC, ETH, SOL, BNB, XRP or other coins: totals, longs versus shorts, ratio, largest event, most affected coin, zero-filled timelines and history. A spike uses a robust z-score of the last five minutes against a 24-hour baseline of 5-minute buckets:
\[ z = \frac{x - \operatorname{median}(B)}{\max\left(1.4826 \cdot \operatorname{MAD}(B),\; m/4\right)} \]
where $m$ is the minimum notable amount (\$250{,}000). A spike needs $z \geq 4$ and $x \geq m$. A burst is at least 15 events for one coin within 60 seconds, and an imbalance shift is a change of at least 35 points in the long share. Alerts have a 30-minute cooldown and can be sent to Telegram.

\subsection{Context and Explanation}
\texttt{/api/liquidations/context/\{symbol\}} places liquidations next to price, volume, open interest, funding and volatility from Binance futures, and lists scenarios consistent with the evidence, each with supporting and contradicting points. It never claims that liquidations decide future price. \texttt{/api/liquidations/explain} returns a rules-based or grounded AI explanation.

\section{Verification, Constraints and Recommendations}
\subsection{Verification Status}
\begin{itemize}
\item The backend test suite was executed: \texttt{python -m unittest discover -s tests} ran \textbf{65 tests, all passed}. The tests cover liquidation parsing, duplicates, windows, spikes and alerts, grounded number checks, the no-fake-data rules, specialists, the chat endpoint, risk copilot, key levels, the database, Telegram and the watcher.
\item The backend and frontend were run together against live Binance data; the public GET endpoints returned HTTP 200, 94 live liquidation messages were received with none invalid, and a Copilot question was answered in about 2.4 seconds.
\item \texttt{flutter analyze} reported no errors and \texttt{flutter build web} succeeded. The frontend has no automated widget tests yet (the broken template test was removed).
\item This documentation was generated from the current source; the appendix catalog was extracted automatically.
\end{itemize}

\subsection{Known Constraints}
\begin{itemize}
\item Direction prediction remains weak: holdout accuracy is below always-neutral accuracy, although macro-F1 and confident accuracy are higher.
\item The deployed models use two years of history; better ten-year candidate models exist but are not yet deployed.
\item Liquidations are a sample from one exchange (at most one event per symbol per second).
\item Whale, crypto-linked stock, language-model and Telegram features require keys; without them they are unavailable.
\item The default CORS wildcard and the placeholder JWT secret require production configuration.
\item \texttt{create\_all} is not a migration strategy. SQLite and in-process cache/jobs require care in multi-instance deployment.
\item Language-model integrations add latency, cost and privacy considerations; the number check prevents invented figures but not every wording error.
\end{itemize}

\subsection{Recommendations}
\begin{itemize}
\item Deploy the ten-year models and calibrated downside-risk models for several horizons.
\item Add data with new information: options-implied volatility, recorded open interest and order-book depth.
\item Add Flutter widget tests for navigation and core screens, and API tests with mocked providers.
\item Use database migrations, a production CORS allowlist, stable secrets, backups and structured monitoring.
\item Track model drift and calibration in a live forward test; publish class-specific metrics and baselines.
\item Disclose the chat context sent to external language models.
\end{itemize}

\section{Conclusion}
CryptoSense AI is a modular market-observation and learning platform combining Flutter, FastAPI, SQLAlchemy, live market data, interpretable risk factors, an ML ensemble, liquidation intelligence, alerts, simulated trading and a Risk Copilot with grounded, retrieval-assisted answers.

Since the previous version the project gained liquidation intelligence, the Risk Copilot, six specialist analysts, Claude-based grounded explanations, Quiver and Telegram integrations and a tested code base of 65 automated tests, and it lost every demo and fake data path, the untrained GRU model and several unused pages and scripts. Its strengths are its end-to-end structure, explicit temporal evaluation and honest reporting of unavailable data. Its main limitation is that reliable directional superiority over naive baselines is not demonstrated; downside risk is more predictable than direction.

Future work should prioritize deploying the longer-history and calibrated models, new data sources, frontend tests, operational hardening and live forward testing.
